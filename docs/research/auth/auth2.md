Как сейчас работают 4 пути регистрации

Путь A: Мобильное приложение (чистая установка)
POST /devices { device_id: "hw-uuid" }
→ Создаёт User (анонимный, bot_user_id = NULL)
→ Создаёт UserDevice
→ Telegram НЕ привязан

Путь B: Telegram WebApp (Mini App внутри Telegram)
X-Platform: web + initData
→ Проверяет HMAC initData
→ Находит BotUser по platform_id
→ Создаёт User + UserDevice + СРАЗУ привязывает bot_user_id
→ Всё автоматически ✓

Путь C: Бот → API (бот обращается напрямую)
Bearer: tg_user_id + X-Key: HMAC
→ Только для уже связанных аккаунтов

Путь D: Ручная привязка (key_phrase)
Пользователь установил приложение (Путь A)
→ Потом вводит key_phrase из бота
→ POST /auth/link-telegram { key_phrase }
→ Связывает User ↔ BotUser

Где среди этого веб-кабинет?

Сейчас — нигде. Кабинет только ищет, но не создаёт. Вот как он должен встроиться:

Путь E (НОВЫЙ): Веб-кабинет
POST /v1/auth/telegram { id, first_name, hash... }

    ┌─ BotUser существует?
    │
    ├─ ДА → User привязан?
    │        ├─ ДА → Логин ✓ (как сейчас)
    │        └─ НЕТ → Создать User, привязать, логин ✓
    │
    └─ НЕТ → Создать BotUser + User, привязать, логин ✓

Это по сути тот же Путь B (WebApp), только вместо initData — данные от Login Widget. Логика авто-создания уже существует в UserDeviceService.create_v2() —  
 можно переиспользовать.

Будет ли конфликт с мобильным?

Нет, потому что связка идёт через tg_user_id (уникальный):

1. Пользователь заходит в кабинет → создаётся User с tg_user_id=123
2. Потом ставит мобильное приложение
3. Открывает Mini App или вводит key_phrase
4. Бэкенд находит User по tg_user_id=123 → тот же аккаунт
5. Дубликата нет ✓

Единственный edge case — если пользователь установит мобильное приложение без привязки Telegram (Путь A → анонимный User), а потом зайдёт в кабинет. Тогда  
 будет два User. Но для этого уже есть MergeAccountUseCase — он мёржит аккаунты.

Роль бота во всём этом

Бот не участвует в авторизации кабинета напрямую. Его роль:

┌───────────────────────┬────────────────────────────────────────────────────────────────────────────────────────────────────────┐
│ Функция │ Как связан с кабинетом │
├───────────────────────┼────────────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Токен для HMAC │ Telegram подписывает данные виджета токеном бота — бэкенд проверяет подпись тем же токеном │
├───────────────────────┼────────────────────────────────────────────────────────────────────────────────────────────────────────┤
│ BotUser как хранилище │ Партнёрская сеть, монеты, реферальная цепочка — всё в bot_users, кабинет читает через user.bot_user_id │
├───────────────────────┼────────────────────────────────────────────────────────────────────────────────────────────────────────┤
│ key_phrase для связки │ Если пользователь потом ставит мобильное приложение, бот генерирует key_phrase для merge │
├───────────────────────┼────────────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Домен в BotFather │ У бота должен быть разрешён домен diaverse.app для Login Widget │
└───────────────────────┴────────────────────────────────────────────────────────────────────────────────────────────────────────┘

Бот — это не сервис авторизации, а якорь идентификации: один Telegram ID = один bot_users.platform_id = один аккаунт на всех платформах.
