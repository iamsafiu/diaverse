# Original Modules Specification

ТЗ: Архитектура личного кабинета Diaverse (web)

1. Общая концепция
   Разработать веб-версию личного кабинета Diaverse с модульной архитектурой и системой ролей.
   Цель:
   заложить масштабируемую архитектуру
   обеспечить гибкое управление ролями и доступами
   подготовить систему под расширение (2 увроня партнерки , контент, финансы, обучение и т.д.)
2. Уровень архитектуры (High-Level)
   Тип архитектуры:
   Frontend: (React / Next.js)
   Backend: Технологии:
   Python 3.11+
   FastAPI
   PostgreSQL
   SQLAlchemy / SQLModel

Auth: JWT + Telegram OAuth (в будущем email)
DB: PostgreSQL
Хранение файлов: S3-совместимое (например, Yandex Object Storage) 3. Система ролей
На первом этапе заложить 3 роли:

1. User (Пользователь)
   Базовый доступ:
   просмотр личного профиля
   базовые разделы (2 тестовых модуля)
   доступ к партнёрской структуре (ограниченный)
2. Partner (Партнёр)
   Расширенный доступ:
   Раздел "Партнёры":
   реферальная структура:
   1 линия
   2 линия
   метрики:
   количество приглашённых
   активные / неактивные
   статус партнёра
   реферальная ссылка
   базовая аналитика
3. Employee (Сотрудник)
   Расширенный доступ ко всем модулям:
   управление пользователями
   доступ к данным партнёров
   доступ к контенту / выплатам / системе
   ⚠️ Важно: роли должны быть расширяемыми (RBAC)
4. Админ-панель (отдельный модуль)
   Назначение:
   Централизованное управление системой
   Функционал:
   создание / редактирование ролей
   настройка прав доступа (RBAC)
   управление пользователями
   включение/выключение модулей
   управление контентом
   управление выплатами (заглушка)
5. Модульная структура
   Система должна быть разбита на модули (feature-based architecture)
   Базовые модули (пример):
6. Profile
   личные данные (как на скрине)
   контакты
   безопасность
7. Dashboard(заглушка)
   краткая статистика
   активность
8. Partners
   структура
   рефералы
   аналитика
9. Finance (заглушка)
   доходы
   выплаты
10. Content Factory (заглушка)
    контент
    задания
11. Team(заглушка)
    команда
12. Tools(заглушка)
    инструменты
13. Education(заглушка)
    обучение
14. Leaderboard(заглушка)
    рейтинг

15. Структура frontend (пример)
    /src
    /modules
    /auth
    /profile
    /partners
    /finance
    /admin
    /shared
    /ui
    /api
    /hooks
    /layouts
    /pages
16. Структура backend (пример)
    /src
    /modules
    /auth
    /users
    /roles
    /partners
    /admin
    /common
    /guards
    /middlewares
17. RBAC (ключевая часть)
    Реализовать систему:
    Role
    Permission
    RolePermission
    UserRole
    Пример:
    User → Role → Permissions → Modules → Actions
    Должно быть:
    гибкое добавление новых ролей
    возможность включать/выключать доступ к модулям
18. Партнёрская система (основа MLM)
    Данные:
    user_id
    parent_id (кто пригласил)
    линия (1 / 2 / n)
    статус (active / inactive)
    агрегация статистики
19. Авторизация (на будущее, но учесть в архитектуре)
    email/password
    Telegram login (обязательно предусмотреть)
    guest mode (ограниченный доступ)
20. UI/UX (по референсу)
    Опора на твой скрин:
    левое меню (sidebar)
    верхняя навигация внутри раздела
    карточки с данными
    модульность интерфейса
21. Требования к масштабируемости
    Обязательно:
    модульность (каждый раздел = отдельный модуль)
    независимость модулей
    возможность добавления новых ролей без переписывания системы
    возможность подключения новых источников авторизации

Окей, теперь у меня полная картина. Давай разложим всё честно.

4. Партнёрская система (слишком поверхностно)

ТЗ описывает user_id, parent_id, линия — это наивная модель. MLM-дерево на senior уровне:

                      User A
                     /      \
                User B      User C     ← Линия 1
               /    \          \
            User D  User E   User F    ← Линия 2

    ┌─────────────────────────────────────────────────┐
    │ Что нужно для production MLM-дерева:            │
    ├─────────────────────────────────────────────────┤
    │ • Materialized Path или Nested Set в PostgreSQL │
    │   (ltree extension — идеально для деревьев)     │
    │ • Рекурсивные CTE запросы (WITH RECURSIVE)      │
    │ • Кэширование агрегатов (Redis / materialized)  │
    │ • Event sourcing для начисления бонусов         │
    │ • Защита от циклических ссылок                   │
    │ • Лимит глубины дерева                          │
    │ • Batch-пересчёт статистики (не real-time)       │
    └─────────────────────────────────────────────────┘
