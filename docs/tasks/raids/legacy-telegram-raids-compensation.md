# Компенсация старых Telegram-рейдов

[Back to Docs](../../README.md)

Дата первичного аудита: 2026-06-03  
Дата уточнения экономики: 2026-06-04

Документ фиксирует схему закрытия старых рейдов Telegram-бота при переходе на новую механику рейдов Diaverse.

Фактическое уточнение от 2026-06-04: старые рейды в Telegram-боте уже были отключены примерно за 2 дня до этого, то есть идеальный переходный лаг нельзя запустить как будущий процесс. Поэтому текущая схема должна исходить из уже случившегося отключения.

## Короткий вывод

Выгрузка `raids-tg-bot.csv` содержит только активные старые рейды, не фабрику и не полный дамп.

Позиция экономики:

- В идеальном сценарии USDT-рейды и 1-дневные рейды не компенсируются отдельно, а доходят за переходные 2 дня.
- Но старые рейды уже отключены, поэтому нужно проверить, действительно ли короткие рейды и USDT-рейды вернулись.
- Если 1-дневный или USDT-рейд не вернулся после отключения, это исключение для manual audit, а не обычная массовая компенсация.
- 7- и 30-дневные рейды нужно компенсировать деньгами, а не ресурсами.
- Денежная компенсация должна быть в XDV: игроки смогут сами купить нужные ресурсы на бирже, а новая экономика получит больше сделок.

Итоговая стратегия: фактологический аудит возврата коротких рейдов, manual handling для не вернувшихся 1-дневных/USDT, XDV-компенсация для длинных 7/30-дневных рейдов.

## Фактический статус отключения

Идеальный порядок был таким:

1. Включить новые рейды в приложении.
2. Не отключать старые рейды в Telegram-боте сразу.
3. В Telegram-боте закрыть возможность отправлять новых пэтов в рейды.
4. Оставить старые активные 1-дневные и USDT-рейды доходить естественно.
5. Через 2 дня отключить старые рейды в Telegram-боте полностью.
6. После отключения начислить компенсацию только по оставшимся legacy-рейдам длительностью 7 и 30 дней.

Но этот порядок уже нельзя выполнить буквально, потому что старые рейды отключили раньше. Поэтому документ дальше описывает emergency/post-factum вариант.

Фактическая схема:

```text
2026-06-02 примерно
  старые рейды в Telegram-боте уже отключены

2026-06-04
  проверить, кто реально вернулся
  1-дневные и USDT-исключения отправить в manual audit
  7/30-дневные legacy-рейды компенсировать XDV
```

Обязательная первая проверка после фактического отключения:

- по `user_character_id` проверить, вернулся ли пэт из старого рейда;
- по `total_days = 1` и `payment_type = USDT` составить список исключений, если пэт не вернулся;
- не начислять массовую компенсацию коротким рейдам, если они уже корректно закрылись;
- не терять пользователей, у которых короткий рейд был оборван отключением.

## Что компенсируем

Массовая компенсация нужна только для рейдов, которые нельзя было нормально дождаться без длинного лага:

| `total_days` | Решение |
| ---: | --- |
| 1 | Если вернулся - не компенсировать; если не вернулся - manual audit |
| 7 | Компенсировать XDV |
| 30 | Компенсировать XDV |

USDT-рейды по словам экономики обычно не бывают длиннее 1 дня. Поэтому они не входят в массовую XDV-компенсацию длинных рейдов.

Если после фактического отключения найдутся не вернувшиеся USDT-рейды или 1-дневные рейды, они должны попасть в manual audit как исключение. Для таких исключений безопаснее либо вручную вернуть ожидаемый результат, либо выдать отдельную полную денежную компенсацию по решению экономики/support.

## Почему XDV, а не ресурсы

Ресурсные пакеты не являются финальной рекомендацией.

Причины перейти к XDV:

- это проще объяснить пользователям;
- это проще начислить и проверить;
- игрок сам решает, что купить под новую механику;
- биржа получит дополнительный оборот;
- не нужно угадывать, какой ресурс был бы справедливым для старой механики;
- не нужно балансировать `bullet`, `galaglue`, `nuclear_acorn`, `synthesis_core`, `slot_token` для legacy-пакетов.

Шкатулки также не выдаются:

- старый `loot` пустой;
- случайная выдача создаст несправедливость;
- редкий удачный ролл может ударить по экономике сильнее, чем XDV.

## Формула XDV-компенсации

Каждая строка 7- или 30-дневного рейда считается отдельно:

```text
xdv_compensation =
  base_location_xdv
  * duration_multiplier
  * progress_multiplier
  * nft_multiplier
  * golden_multiplier
```

После расчета строки компенсации суммируются по пользователю.

## Базовые суммы по локации

Базовая сумма должна отражать ценность локации и старое ожидание игрока.

Фактически использованный вариант 2026-06-04:

| Старый рейд | `base_location_xdv` |
| --- | ---: |
| Rusty Wastelands | 200 |
| Oasis | 500 |
| Radioactive Cave | 1200 |

Эта таблица была использована в фактическом начислении 2026-06-04.

## Множитель длительности

| `total_days` | Множитель |
| ---: | ---: |
| 7 | 1.00 |
| 30 | 4.00 |

30-дневный рейд не должен считаться как 30 отдельных 1-дневных рейдов, иначе сумма может стать слишком большой. Но он должен быть ощутимо дороже 7-дневного, потому что блокировал пэта и ожидание результата намного дольше.

## Множитель прогресса

Прогресс считается по старым полям:

```text
progress = current_day / total_days
remaining = total_days - current_day
```

Рекомендуемая таблица:

| Условие | Множитель |
| --- | ---: |
| `remaining <= 0` | 1.00 |
| `progress >= 0.75` | 0.90 |
| `progress >= 0.50` | 0.70 |
| `progress >= 0.25` | 0.50 |
| `progress < 0.25` | 0.30 |

Минимальный floor `0.30` нужен, потому что рейды закрываются не по вине пользователя.

## Множители NFT и golden

| Флаг | Множитель |
| --- | ---: |
| `with_nft = true` | 1.25 |
| `with_nft = false` | 1.00 |
| `is_golden = true` | 1.05 |
| `is_golden = false` | 1.00 |

`is_golden` не должен давать большой бонус, потому что таких записей 753 из 781. Большой golden-множитель почти равен глобальному раздуванию компенсации.

## Округление и caps

Рекомендуемые правила:

- сумму строки округлять вверх до целого XDV;
- итог по пользователю округлять вверх до целого XDV;
- ставить cap на одну строку и на пользователя;
- все caps утвердить с экономикой перед начислением.

Черновые caps:

| Ограничение | Значение |
| --- | ---: |
| Cap на одну строку | 10000 XDV |
| Cap на одного пользователя | 100000 XDV |

Caps нужны для защиты от ошибок входных данных и неожиданных мультипликаторов.

## Распределение пользователям

Технический порядок:

1. Загрузить CSV как legacy source.
2. По каждой строке проверить текущее состояние `user_character_id`.
3. Разделить строки на три группы:
   - `resolved_short`: `total_days = 1` или `payment_type = USDT`, пэт уже вернулся;
   - `manual_short`: `total_days = 1` или `payment_type = USDT`, пэт не вернулся;
   - `compensate_long`: `total_days IN (7, 30)`.
4. Для `resolved_short` ничего не начислять, только сохранить audit.
5. Для `manual_short` передать список в support/economy на ручное решение.
6. Для `compensate_long` найти `user_characters.uuid = user_character_id`.
7. По найденному пэту определить `user_id`.
8. Если пользователь найден, добавить XDV-компенсацию в агрегат пользователя.
9. Если пэт не найден, записать строку в unresolved audit.
10. Суммировать long-компенсации по пользователю.
11. Начислить одним аудируемым fulfillment/support batch на пользователя.
12. Сохранить metadata: исходный CSV, raid row id, old raid id, location, total days, current day, progress, multipliers, formula version, shutdown status.

Схема:

```text
raids-tg-bot.csv
      |
      v
check current pet/legacy status
      |
      +--> resolved_short: audit only
      |
      +--> manual_short: support/economy exception
      |
      v
compensate_long: total_days in (7, 30)
      |
      v
user_character_id -> user_characters -> user_id
      |
      v
per-user aggregated XDV compensation
      |
      v
cabinet fulfillment / support grant
      |
      v
XDV balance credit
```

## Коммуникация пользователю

Текст должен быть прямым:

```text
Мы переносим рейды из Telegram-бота в новую механику приложения.
Новые отправки в старые рейды закрыты.
Короткие старые рейды проверяются отдельно: если они завершились, дополнительная компенсация не нужна.
Длинные старые рейды на 7 и 30 дней закрыты денежной XDV-компенсацией.
Отдельно проверяем, что legacy-состояние пэтов не оставило их недоступными.
```

Важно не обещать, что это точный результат старого рейда. Это компенсация за переход механики.

## Решения

- Зафиксировать, что старые рейды уже отключены примерно 2026-06-02.
- Не использовать переходный лаг как будущий план, только как критерий проверки.
- Проверить, вернулись ли 1-дневные и USDT-рейды после фактического отключения.
- Не начислять массовую компенсацию коротким рейдам, если они вернулись.
- Не вернувшиеся 1-дневные и USDT-рейды отправлять в manual audit.
- Компенсировать только 7- и 30-дневные legacy-рейды: выполнено для 135 пользователей с `bot_user_id`.
- Компенсировать XDV, а не ресурсами: выполнено.
- Не выдавать случайные шкатулки.
- Суммировать компенсации по текущему владельцу `user_character_id`.
- Проверить legacy-состояние пэтов отдельно от денежного начисления.
