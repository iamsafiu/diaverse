# Notification badge stayed stale after reward grants

**Date:** 2026-04-30 09:07
**Files:** diaweb/frontend/modules/notifications/hooks.ts, diaweb/frontend/modules/advent/hooks/useClaimAdventDay.ts, diaweb/frontend/modules/advent/components/AdventPaymentStubPage.tsx, diaweb/frontend/modules/shop/hooks/usePurchase.ts, diaweb/frontend/__tests__/modules/advent/useClaimAdventDay.test.tsx, diaweb/frontend/__tests__/modules/shop/usePurchase.test.tsx
**Severity:** medium

## Problem

After a user received a reward, the notification was present in the popup list, but the blue unread badge and count on the bell did not appear until a page refresh.

## Root Cause

The popup list is fetched when the panel opens, so it could see newly created notifications. The bell badge uses the separate `notifications.summary` query, and reward-producing actions only invalidated their own domain queries: Advent calendar state, hosted checkout state, or shop catalog state. The summary query therefore kept its previous unread count until its polling interval or a full page refresh.

## Solution

Exported a shared notification query invalidation helper and called it after successful Advent claim, successful Advent hosted checkout finalization, and completed shop purchase. The active summary query now refetches immediately after those actions, so the unread badge appears without a page reload. Added tests for Advent claim and shop purchase invalidation.

## Prevention

Any feature that creates a user-facing notification must invalidate the notification root query in the same success path that updates its own domain data. Tests for notification-emitting mutations should assert both domain query invalidation and notification query invalidation.
