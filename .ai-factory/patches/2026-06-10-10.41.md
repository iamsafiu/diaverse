# Crypton offer card hides counter price

**Date:** 2026-06-10 10:41
**Files:** diaweb/frontend/modules/crypton/components/CryptonOfferCard.tsx, diaweb/frontend/modules/i18n/dictionaries/{ru,en}.json, diaweb/frontend/__tests__/modules/crypton/CryptonOfferCard.test.tsx
**Severity:** medium

## Problem

When staff/Crypton responded with a counter price, the user-facing Crypton offer card on the offers page still displayed only the user's proposed price. The backend and frontend state already carried `decisionPrice`, but the compact offers card did not render it.

## Root Cause

`CryptonOfferCard` rendered only `selectedOffer.proposedPrice` in its description block. Earlier detail/status surfaces had support for both proposed and decision prices, but the compact card was not updated when counter-price data was added to the selected offer summary.

## Solution

The card now formats both proposed and decision prices, keeps the user's price visible, and conditionally renders the Crypton price when it exists and differs from the user's price. User-facing dictionary labels were renamed from generic "decision price" wording to "Crypton price". A regression test covers a countered offer card with both values.

## Prevention

- When adding fields to `CryptonSelectedOfferSummary`, audit every consumer of `selectedOffer`, not only the detail page.
- Counter-offer flows should assert both the original user value and the staff/Crypton value in compact and detail UI tests.
- Avoid replacing source values with decision values in display helpers unless the UI explicitly calls for a single accepted-payment amount.
