# Zion null invoice status shop alert noise

**Date:** 2026-05-14 17:43
**Files:** diaverseapi/app/cabinet/payments/zion/service.py, diaverseapi/tests/test_cabinet_zion_payments.py
**Severity:** medium

## Problem

Opening a Zion crypto shop checkout without paying created
`shop.payment.provider_status_unsupported` alerts. Zion returned a hosted invoice
payload with `status: null` and `payment_created_at: null`; the backend normalized
the empty invoice status to `UNKNOWN` and treated it as an unsupported provider
status.

## Root Cause

The Zion invoice reconciliation path did not distinguish an absent invoice status
from a real unknown status string. For unpaid hosted invoices, Zion can return
`status: null` before a final payment exists. The backend correctly kept the local
payment in `awaiting_payment`, but the shop alert path still interpreted the
normalized `UNKNOWN` as an actionable provider contract problem.

## Solution

Added a helper that checks whether a provider status contains actual status text.
Empty Zion invoice status values now map to `awaiting_payment` without warning or
shop alert. Real unknown non-empty strings still flow through the existing
unsupported-status alert path.

## Prevention

- Preserve the distinction between missing provider fields and unknown provider
  values when normalizing external statuses.
- For hosted checkout providers, test unpaid invoice payloads separately from
  paid payment payloads.
- Avoid adding catch-all normalized statuses to allowlists when the raw provider
  value carries important semantics.
