# Canonical referral link failed when an existing claim met a new share session

**Date:** 2026-07-27 15:49
**Files:** `diaverseapi/app/referrals/links.py`, `diaverseapi/tests/test_referrals_links_db.py`, `diaweb/frontend/modules/referrals/components/ReferralInviteCard.tsx`, `diaweb/frontend/__tests__/modules/referrals/ReferralInviteCard.test.tsx`
**Severity:** high

## Problem

Opening a newly generated referral share URL could return HTTP 500 when the visitor already had a current claim for the inviter. The web UI then displayed its generic invitation-processing error. The share UI also exposed a different tracking short URL after every copy/share action instead of consistently sharing the inviter's canonical URL.

## Root Cause

The attribution service correctly reused the visitor's existing current claim, but `bind_share_session` assumed that this claim had not already been bound to another share session. Assigning the same claim to a second session violated the unique `bound_claim_id` constraint during SQLAlchemy autoflush, producing an unhandled `IntegrityError` instead of the expected safe share-session mismatch.

The frontend made the problem common by using the newly created analytics session URL as the public URL for every share action, even though it had already loaded the canonical referral URL.

## Solution

The backend now locks the claim, checks for an existing share-session binding before mutation, logs a privacy-safe `[FIX:referral-single-link]` event, and returns the existing domain mismatch path. The API already treats this mismatch as non-fatal and continues resolving the canonical invitation.

The frontend still records bounded copy/share analytics events, but it always places the canonical referral URL in clipboard, browser-share, and native-share payloads. Regression tests distinguish the canonical URL from the tracking URL and verify that duplicate claim binding leaves the new analytics session unbound without causing a database integrity failure.

## Prevention

- Treat canonical referral identity and share analytics as separate concerns.
- Never expose an analytics-session URL when the product contract promises one stable personal link.
- Before assigning a uniquely constrained foreign key, handle the existing-owner case as an idempotent domain outcome.
- Cover both directions of reuse: one share opened by many visitors and one visitor opening multiple share attempts.
- Keep database-backed regression coverage for ORM autoflush and uniqueness behavior; mocks alone cannot reproduce this failure.
