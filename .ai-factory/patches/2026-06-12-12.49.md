# Duplicate saved raid slot while run is ready

**Date:** 2026-06-12 12:49
**Files:** diaweb/frontend/modules/raids/components/RaidLocationStack.tsx, diaweb/frontend/modules/raids/components/RaidSlotGrid.tsx, diaweb/frontend/__tests__/modules/raids/RaidLocationStack.test.tsx
**Severity:** medium

## Problem

After a raid finished, the same pet could be shown twice in the slots sheet:
one runtime card in the ready state and one saved team-slot card with a remove
button. This looked like duplicated command slots and made the user think the
team had been duplicated.

## Root Cause

The slots grid rendered runtime slots and saved team slots as separate visual
layers. When a saved team pet also existed in an active or completed run, the
empty placeholder for the saved slot could still render the saved pet, even
though the ready runtime card already represented that same pet. The selected
location also passed saved team slots without narrowing them to the currently
selected raid mode.

## Solution

The selected location now passes only saved team slots for the current mode.
The slot grid suppresses saved team-slot placeholders whose pet is already
visible through an active or completed run in the same location and mode. The
saved team data remains intact and reappears after the ready run is collected.
A development-only `[FIX:raids-slot-duplicates]` log records suppressed
duplicates for debugging.

## Prevention

When UI combines persistent configuration state with runtime state, runtime
cards should take display precedence. Tests should cover the overlap case where
a persistent saved slot and a completed runtime slot reference the same pet.
