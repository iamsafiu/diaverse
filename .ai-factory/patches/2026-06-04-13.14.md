# Raid slots used future grade-balance thresholds with ordinary user grade

**Date:** 2026-06-04 13:14
**Files:** `diaverseapi/app/raids/catalog/data/raids_catalog.v1.yaml`, `diaverseapi/app/raids/tests/test_catalog.py`, `diaverseapi/app/raids/tests/test_domain_rules.py`
**Severity:** high

## Problem

Raid XDV slot limits did not visibly increase for users raising ordinary grade levels. Grades `0..9` stayed in the same `0-10` slot-table bucket and kept 2 basic XDV slots.

## Root Cause

The raid catalog encoded future grade-balance thresholds (`0-10`, `10-25`, `25-50`, ...), but the implementation currently feeds ordinary `users.grade` into `raid_profiles.profile_grade`. Ordinary grade is the available production field, so the future balance thresholds made most ordinary grade increases ineffective.

## Solution

Changed the raid slot table to ordinary grade buckets: `0`, `1`, `2`, ..., `8`, `9+`. This preserves the existing min/max slot economy (`2..11` basic, `4..22` subscription) while making each ordinary grade increase unlock the next slot tier until the cap.

## Prevention

When a product document references a future balance-derived field, either implement the field first or add an explicit temporary mapping from current production fields. Regression tests should cover realistic production values, not only future balance thresholds.
