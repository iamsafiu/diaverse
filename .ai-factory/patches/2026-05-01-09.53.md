# Reuse shop special offers on offer set edit

**Date:** 2026-05-01 09:53
**Files:** diaverseapi/app/cabinet/shop/specials/service.py, diaverseapi/tests/test_cabinet_shop_specials.py
**Severity:** high

## Problem

Editing an existing shop special offer set via `PATCH /v1/admin/shop/specials/offer-sets/{id}` returned `500 Internal Server Error`.
Backend logs showed `UniqueViolationError` for `uq_cab_shop_item_offers_code` on `(shop_item_id, offer_code)`.

## Root Cause

The update flow deactivated old slot offers and deleted slot rows, but then inserted new `CabShopItemOffer` rows using the same deterministic `offer_code` (`special:{set_id}:{slot_index}`). When the same shop item remained in the same slot, the old deactivated offer still existed and the unique constraint rejected the duplicate insert.

## Solution

The slot replacement flow now loads existing offer IDs by slot before deleting slot rows. For each incoming slot, it reuses and updates the existing special offer row when possible, falling back to lookup by `(shop_item_id, offer_code)` and only inserting when no reusable offer exists.

## Prevention

- For deterministic offer codes, update existing rows instead of inserting replacements.
- When deleting child slot rows but preserving related offer rows, explicitly define whether related rows are reused, soft-deactivated, or physically removed.
- Cover edit flows where a slot keeps the same shop item and offer code.
