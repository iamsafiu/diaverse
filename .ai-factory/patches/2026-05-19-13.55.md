# Club Benefit Duplicate Slot and Userbot Peer Resolution

**Date:** 2026-05-19 13:55
**Files:** `aibot/app/application/use_cases/club_benefit.py`, `aibot/services/userbot_service.py`, `diaweb/frontend/modules/copywriting/components/ClubBenefitPanel.tsx`
**Severity:** medium

## Problem

The staff copywriting club tab could show two "useful" club posts even though the product requirement is one post. Publishing to the club group could also fail with `Peer id invalid: -1003759564801`.

## Root Cause

Club benefit scheduling still used a default and max slot count of two, so the worker could create two active daily benefit rows. Existing data also remained active after the UI was changed to request one slot. For publishing, Pyrogram can fail to resolve raw `-100...` peer ids when the userbot session has not warmed its dialog peer cache, especially after the account was just added back to the group.

## Solution

Limit club benefit generation to one slot in the backend, add a migration that deactivates existing active slots above one, and make the frontend display only the first club benefit as a defensive guard. Add a userbot fallback that scans dialogs when `get_chat(-100...)` fails with peer-id-invalid and returns the matching dialog metadata.

## Prevention

Keep scheduled rubrics' default counts aligned with their UI contract. Add tests for count clamps and one-card UI helpers. For Telegram userbot publishing, resolve numeric group ids through dialogs before treating `Peer id invalid` as a permanent configuration failure.
