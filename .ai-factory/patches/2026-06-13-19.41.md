# Copywriting edit access did not allow Club10000 broadcasts

**Date:** 2026-06-13 19:41
**Files:** `diaverseapi/app/cabinet/rbac/staff_modules.py`, `diaverseapi/app/cabinet/rbac/service.py`, `diaverseapi/tests/test_cabinet_rbac_service.py`, `docs/features/copywriting/club10000-broadcasts.md`
**Severity:** medium

## Problem

A staff employee with access to the copywriting workspace could open the Club10000 broadcast surface but could not send a test broadcast or enqueue a campaign. The BFF minted an internal JWT from `/v1/staff/access/me`, and the downstream `aibot` routes required `copywriting.club.broadcast:send`, which was not included in copywriting module edit claims.

## Root Cause

The original Club10000 broadcast rollout intentionally kept `copywriting.club.broadcast:send` separate from ordinary copywriting staff access. The staff access matrix, however, only exposes module-level view/edit toggles and has no separate broadcast-specific toggle. As a result, granting `copywriting` edit access looked sufficient to operators but still omitted the exact permission required by `aibot`.

## Solution

Added `copywriting.club.broadcast:send` to the `copywriting` staff module edit permissions. Kept `copywriting.broadcast:send` excluded so auth-bot broadcasts remain separately restricted. Added a regression assertion in the RBAC service test and a debug log with the `[FIX:copywriting-club-broadcast-access]` prefix when staff permission claims are built.

Updated the Club10000 broadcast documentation to state that copywriting edit access grants Club10000 broadcast send access, while the base `employee` role alone still does not.

## Prevention

- When adding a staff action behind a granular permission, ensure the admin UI has a way to grant that permission.
- If the UI only exposes module view/edit toggles, map edit claims to all actions expected by operators inside that module.
- Add tests for both the granted action and any intentionally excluded sibling action.
