# Crypton expired cards and catalog request limits

**Date:** 2026-05-28 09:32
**Files:** `diaverseapi/app/cabinet/offers/crypton/service.py`, `diaverseapi/app/cabinet/offers/crypton/catalog_policy.py`, `diaverseapi/tests/test_cabinet_crypton.py`, `diaweb/frontend/modules/crypton/components/CryptonOfferBuilder.tsx`, `diaweb/frontend/modules/crypton/constants.ts`, `diaweb/frontend/modules/crypton/index.ts`, `diaweb/frontend/__tests__/modules/crypton/CryptonOfferBuilder.test.tsx`
**Severity:** medium

## Problem

Expired Crypton offers could stay visible on the offers page with a zeroed timer. The Crypton catalog request dialog also prevented quantities above the catalog max, prefilled the proposed price with the recommended price, and blocked prices below the previous server-side minimum ratio.

## Root Cause

The backend card projection kept `visible=True` for expired requests and claimed windows during cooldown, so the frontend rendered cards whose timers had already elapsed. Separately, both frontend and backend treated catalog max units and minimum price ratio as hard request constraints even though the product flow needs free user input.

## Solution

Expired request cards now return `visible=False` with `decision_expired`, and claimed windows whose `expires_at` is in the past return `visible=False` with `window_expired`. Non-unique catalog offers now expose an effectively unbounded max while preserving the unique-item guard, and the frontend request dialog no longer clamps units, auto-fills the recommended price, or blocks prices below the recommendation/minimum ratio.

## Prevention

Keep backend `offer_card.visible` as the source of truth for whether offer hub cards render. When product copy describes a value as recommended, avoid using it as an implicit validation boundary unless the requirement explicitly says it is a hard limit. Regression tests should cover terminal card visibility and catalog form behavior.
