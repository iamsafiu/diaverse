# Club leaderboard participant names

**Date:** 2026-05-24 22:58
**Files:** `diaverseapi/app/club/repositories.py`, `diaverseapi/app/club/leaderboards.py`, `diaverseapi/app/club/pairing.py`, `diaverseapi/tests/test_club_leaderboards.py`
**Severity:** medium

## Problem

Club leaderboards could show a linked account username such as `@he_mor` instead of the participant's current Telegram name. The member roster used Telegram fields, so the same person appeared as a normal club member in one view and as a stale linked-user handle in the rating.

## Root Cause

`list_active_membership_display_labels()` collapsed manual labels and linked `users` usernames into one string before leaderboard rendering. The leaderboard label helper then preferred that collapsed string over `club_memberships.telegram_first_name` and `telegram_last_name`.

## Solution

Separated display-label context into manual access labels and linked-user fallback labels. Leaderboards and buddy pair labels now use this priority:

1. Manual club display name.
2. Telegram first/last name.
3. Telegram username.
4. Linked user public username or username fallback.
5. Membership/user id fallback.

Added `[FIX:club-leaderboard-labels]` logs when a Telegram name intentionally overrides a linked-user label.

## Prevention

- Keep source-specific label fields separate until final rendering so fallback priority stays explicit.
- Cover individual and buddy leaderboard labels where a linked user handle differs from Telegram first name.
