# Factory subscription entitlement aliases

**Date:** 2026-06-13 12:15
**Files:** diaverseapi/app/factory/domain/modifiers.py, diaverseapi/app/factory/infrastructure/subscription_resolver.py, diaverseapi/app/factory/tests/test_subscriptions.py
**Severity:** high

## Problem

Factory subscription bonuses could be missing for users with active Step Pass subscriptions. The factory resolver recognized only `factory_step_pass_pro` and `factory_trademaster`, while web-store Step Pass grants and existing subscription checks commonly use `pro_fitness_pass` and `premium_fitness_pass`.

## Root Cause

Factory feature keys were introduced as product-specific concepts, but real entitlement rows were not guaranteed to carry those new keys. Other domains had already been adapted to read personal Step Pass subscription sources and legacy feature keys, but the factory resolver still filtered strictly by the two factory-only feature names.

## Solution

Added a factory subscription feature normalization layer. `pro_fitness_pass` now maps to canonical `factory_step_pass_pro`, `premium_fitness_pass` maps to canonical `factory_trademaster`, and legacy dotted factory keys are normalized too. The resolver casts enum values to strings before filtering so legacy enum values can be matched safely without requiring immediate data cleanup. Regression tests cover shop entitlement aliases, legacy dotted keys, canonical feature output, and expiry calculation.

## Prevention

- Subscription resolvers should normalize entitlement aliases at domain boundaries and expose canonical domain features internally.
- When a product feature is renamed, add compatibility tests for both stored legacy rows and current purchase-flow rows.
- Avoid filtering PostgreSQL enum columns by newly added/legacy literals without a text cast when the Python enum model may lag behind database values.
