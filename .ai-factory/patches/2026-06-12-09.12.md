# Factory warehouse and upgrade feedback fixes

**Date:** 2026-06-12 09:12
**Files:** `diaverseapi/app/factory/services/state_service.py`, `diaverseapi/app/factory/services/warehouse_service.py`, `diaverseapi/app/factory/tests/test_warehouse_service.py`, `diaverseapi/app/factory/tests/test_state_service.py`, `diaverseapi/app/factory/tests/test_compartment_service.py`, `diaweb/frontend/modules/factory/*`, `diaweb/frontend/modules/i18n/*`, `diaweb/frontend/__tests__/modules/factory/*`
**Severity:** medium

## Problem

Factory QA found several connected issues: warehouse cap progress and paused notices appeared for resources before their workshops existed, Trademaster autocollect did not collect in the background, resource upgrades showed "level upgraded" before the timer completed, level-up requirements routed users into compartments before production was built, and plaintext backend traces could be shown directly in the UI.

## Root Cause

Warehouse balances are created ahead of active production, but both backend state metadata and frontend live calculations treated every warehouse balance as producing. Autocollect was only attached to manual transfer-to-storage commands, so state reads never moved lazy-accrued resources into inventory. Upgrade command status was interpreted as final UI completion even when the backend correctly returned a started resource upgrade timer.

## Solution

Added active warehouse key detection in state snapshots and filtered warehouse stopped notifications/refresh timers to active balances only. Added a `background_autocollect` warehouse path that lazy-settles, moves whole pending amounts to storage, and credits inventory for Trademaster during state reads. Updated frontend warehouse live state to respect active/producing status, map titles to include real built levels, upgrade success copy to distinguish timer start from final completion, requirement links to route to production build first, and API error parsing to sanitize non-JSON 5xx bodies.

## Prevention

Warehouse UI should never infer production from the existence of a balance alone; active production must come from building state or backend metadata. Subscription automation needs a state-read or scheduled settlement path, not only manual command hooks. Command `completed` status should be interpreted with returned state metadata when an operation starts a timer.

Regression coverage should include inactive warehouse balances, background autocollect without manual collection, resource upgrade timer copy, single-level life-force game-dollar purchase, and non-JSON server error sanitization.
