# Step Pass shop fulfillment stacks existing subscription coverage

**Date:** 2026-06-02 14:56
**Files:** `diaverseapi/app/cabinet/shop/service.py`, `diaverseapi/tests/test_cabinet_shop_service.py`
**Severity:** high

## Problem

Paid web-store Step Pass purchases could be finalized while producing a `personal_fitness_pass`
without copied reward rows. A same-tier purchase could also overlap an already active manual
`user_subscriptions` grant, so the user paid for a month but did not receive an additional
future month of coverage.

## Root Cause

The Step Pass shop grant path treated `personal_fitness_pass` as the only durable grant target.
It did not inspect existing same-tier `user_subscriptions` coverage before creating a new
personal pass from the current date. It also allowed successful finalization when the reward
copy step returned zero rows, which is unsafe when the standard monthly Step Pass rewards have
not been created yet.

## Solution

The grant path now checks active and future same-subscription coverage before creating or
extending a personal pass. If such coverage exists, the purchased duration is inserted as the
next `user_subscriptions` slot after the latest covered end date. Personal pass grants now
require at least one reward row after the copy attempt; otherwise finalization is blocked with
a logged error so the payment remains retryable/reviewable instead of silently completing with
an empty pass.

Focused async tests cover the stacked subscription case and the empty reward-template guard.

## Prevention

- Step Pass fulfillment should preserve purchased duration across mixed grant ledgers.
- Do not mark paid Step Pass shop orders as finalized when no reward template is available for
  a created personal pass.
- Keep regression tests for overlapping manual subscription coverage and reward-copy races.
