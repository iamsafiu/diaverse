# Club benefit regenerate reused generated post

**Date:** 2026-05-19 14:21
**Files:** aibot/app/application/use_cases/club_benefit.py, aibot/db/repositories/club_benefit_repo.py, aibot/app/api/routes/club_benefits.py, aibot/app/worker/processors/regenerate_club_benefit.py, diaweb/frontend/modules/copywriting/*
**Severity:** medium

## Problem

The "Regenerate" button for a ready club benefit post appeared to do nothing. The frontend called the club benefit generate endpoint, but the backend treated ready benefits as already generated and returned/reused the existing job or record instead of creating a replacement candidate.

## Root Cause

The club benefit flow copied the initial generation path but did not implement the separate regeneration path that daily facts already had. Initial generation is intentionally idempotent by date/slot; regeneration needs a new inactive candidate, a new job kind, activation of the replacement, and a polling-visible status.

## Solution

Added club benefit regeneration as a first-class async flow:

- create replacement candidates in `ClubBenefitRepository`
- enqueue `regenerate_club_benefit` jobs with a short related entity id
- activate the replacement candidate immediately so the API returns a pending state
- add a worker processor that generates the new draft
- make the existing `/club-benefits/{id}/generate` route regenerate when the benefit is already generated
- update frontend club status handling for `regeneration_queued`

## Prevention

Review regenerate buttons against this checklist: the API must create a replacement candidate, the worker registry must include the job kind, and the frontend must show a polling-visible non-terminal status immediately after the mutation.
