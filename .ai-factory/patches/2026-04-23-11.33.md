## Problem

Two cabinet UI details drifted away from the mockup and from the runtime meaning:

- the Advent offer hero showed a countdown like "12h left" while its adjacent track was filled by `todayCalendarDay`, so the bar looked complete near the deadline;
- the cabinet topbar rendered a second profile action beside `Download`, and the header fill from the mockup was not reliably visible in runtime.

## Root Cause

Both issues came from UI layers encoding a stale presentation rule instead of the current product meaning:

- the Advent track reused season-day progress math because it was easy to derive from API payload, but that metric does not describe countdown remaining time;
- the topbar preserved both the navigation-level profile entry and the action-level profile shortcut from the mockup exploration phase, while its gradient fill depended on a utility-class rendering path that was too easy to miss visually.

## Solution

- Reworked the Advent offer progress helper to derive bar percentage from the same time window as the countdown, so the track drains toward the deadline instead of filling by calendar day.
- Removed the artificial minimum fill width so late-stage countdowns can look nearly empty.
- Removed the duplicate profile action from the topbar actions area and left the navigation profile tab as the single profile entry.
- Moved the topbar background fill to an explicit inline `background` style using the mockup gradient values.
- Updated cabinet and offers tests to lock the new behavior.

## Prevention

- When a UI control sits next to a timer, derive both visuals from the same deadline model rather than from a nearby but different progress metric.
- When porting mockup visuals, prefer one explicit source of truth for layered backgrounds if an arbitrary utility value is visually hard to verify.
- Add focused tests for duplicated navigation/action affordances in top-level shells, because those regressions are easy to miss in component-only work.
