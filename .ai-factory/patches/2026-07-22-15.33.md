# Public referral landing never completed auth bootstrap

**Date:** 2026-07-22 15:33
**Files:** `diaweb/frontend/modules/referrals/components/ReferralLandingPage.tsx`, `diaweb/frontend/__tests__/modules/referrals/ReferralLandingPage.test.tsx`
**Severity:** high

## Problem

The public referral landing remained indefinitely on “Checking invitation” even
after the referral BFF and backend had successfully resolved the invitation.

## Root Cause

`ReferralLandingPage` waited for both the pending-referral query and the shared
auth store. The auth store intentionally starts with `isLoading: true`, but the
public `/[lang]/referral` route is outside `CabinetLayout`, which was the only
component that called `fetchUser`. The page-specific provider initialized React
Query only, so auth loading never reached a terminal authenticated or guest
state. Component tests masked the defect by always supplying `isLoading: false`.

## Solution

The public referral landing now starts a guest-capable auth bootstrap with an
explicit route and source label. Safe `[FIX:referral-auth-bootstrap]` logs record
start, completion, or sanitized failure. Zustand selectors keep subscriptions
limited to the required auth fields. A regression test asserts that the public
route invokes `fetchUser` with `allowGuest: true`.

## Prevention

- Every public route that consumes the shared auth store must explicitly own an
  auth bootstrap or render inside a layout that guarantees one.
- Test auth stores from their real initial `isLoading: true` state or assert the
  bootstrap call instead of defaulting directly to a resolved guest state.
- Include public authenticated/guest transition coverage in referral landing
  tests and deployment smoke checks.
