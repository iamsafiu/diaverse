# Raid auto-dispatch polling after completion

**Date:** 2026-06-12 12:27
**Files:** diaweb/frontend/modules/raids/time.ts, diaweb/frontend/__tests__/modules/raids/raid-time.test.ts
**Severity:** medium

## Problem

When a raid finished with auto-dispatch enabled, the UI could stay on the
completed state and show "ready" instead of switching to the next 12 or 24 hour
raid timer. Backend auto-dispatch did create the next run on its worker tick,
but the frontend stopped polling before that happened.

## Root Cause

Raid state polling depended on `next_refresh_at`. Completed raids without
active timers did not receive `next_refresh_at`, so React Query disabled the
refetch interval immediately after the completed state was returned. The
auto-dispatch worker runs asynchronously, which left a short but user-visible
gap where the UI had no reason to request the state that would contain the
newly started auto-dispatched run.

## Solution

The raid refetch helper now keeps a short 2 second polling interval when the
state contains a completed run with an enabled, unpaused auto-dispatch team and
a matching saved team slot. Existing `next_refresh_at` behavior is preserved,
so active runs still refresh at the exact expected timer boundary. A
development-only `[FIX:raids-auto-dispatch-polling]` log records the polling
fallback counts for debugging without adding production console noise.

## Prevention

Frontend polling should account for asynchronous backend follow-up work when
the API intentionally returns a terminal state before the worker has processed
the next transition. Unit tests should cover "terminal state while worker catches
up" cases for time-based game flows, not only active timer states.
