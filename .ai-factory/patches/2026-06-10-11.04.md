# Crypton finalizer failed on mixed timezone Pay1Time dates

**Date:** 2026-06-10 11:04
**Files:** app/cabinet/offers/crypton/payment_finalizer.py, app/cabinet/payments/pay1time/service.py, app/integrations/pay1time/schemas.py, tests/test_cabinet_crypton.py, tests/test_cabinet_pay1time_callback.py
**Severity:** high

## Problem

Paid Crypton requests could remain unfulfilled after Pay1Time confirmed payment. The generic payment session had `status=paid`, but `finalization_status=failed` with `can't compare offset-naive and offset-aware datetimes`, so fulfillment was never started.

## Root Cause

The Crypton finalizer compared `payment_confirmed_at` and `decision_expires_at` directly. Pay1Time callback and invoice status timestamps can be parsed or assigned as timezone-naive `datetime` values, while Crypton decision timestamps are UTC-aware. Python rejects comparisons between naive and aware datetimes.

## Solution

Normalize Pay1Time provider datetime fields to UTC when schemas parse them and again before service persistence. Normalize Crypton finalizer timestamps before expiry comparison and before using the payment confirmed timestamp for paid request state.

## Prevention

Provider datetime values must be normalized at integration boundaries before persistence or comparison. Payment finalizers should defensively normalize persisted datetimes because older rows or provider paths can still carry naive values. Regression tests should include mixed naive/aware datetime comparisons.
