# Duplicate device transfer during Telegram pure login

**Date:** 2026-05-25 17:37
**Files:** `diaverseapi/app/security/usecases.py`, `diaverseapi/tests/test_link_user_device_transfer.py`
**Severity:** high

## Problem

Telegram login/link for a current guest-like account could fail with `UniqueViolation` on `unique_user_devices` when the source user and destination user already had the same `device_id`. In the observed production case, the returning user stayed in a new empty account instead of switching back to the existing Telegram-linked account.

## Root Cause

`LinkUserUseCase` used a bulk `UPDATE user_devices SET user_id = winner` during pure Telegram login and Telegram-to-Telegram silent switch. PostgreSQL allows the same `device_id` to exist for different users, but the unique `(device_id, user_id)` constraint makes the bulk update collide when the destination user already has that device.

## Solution

Added a helper that deletes only source `user_devices` rows whose `device_id` already exists for the destination user, logs moved/discarded counts with `[FIX:auth-device-transfer]`, then updates the remaining device rows. Both `tg_pure_login` and `tg_switch` now use this helper, and success event metadata includes the moved/discarded counts. Added focused unit tests for duplicate and non-duplicate transfer paths.

## Prevention

When moving ownership of rows protected by composite unique constraints, de-duplicate source rows against the destination before running a bulk owner update. Add tests for source/destination collision cases in auth-linking flows.
