# Club leaderboard image regeneration

**Date:** 2026-05-24 19:03
**Files:** `diaverseapi/app/club/aibot_client.py`, `diaverseapi/app/club/leaderboards.py`, `diaverseapi/app/club/admin_api.py`, `diaverseapi/app/club/schemas.py`, `diaverseapi/tests/test_club_leaderboards.py`, `diaweb/frontend/modules/club/api.ts`, `diaweb/frontend/modules/club/components/ClubLeaderboardsPanel.tsx`, `diaweb/frontend/__tests__/modules/club/ClubLeaderboardsPanel.test.tsx`
**Severity:** medium

## Problem

The staff "regenerate image" action for club leaderboards reused the existing generated photo instead of creating a new one when the leaderboard snapshot and image creative config had not changed.

## Root Cause

The aibot request used a deterministic idempotency key built from the leaderboard snapshot hash and image config hash. For an unchanged snapshot/config pair, a repeated request hit the same aibot asset and returned the old `image_path`.

## Solution

Added an explicit `force_regenerate` flow. The frontend sends it when an existing/ready image is regenerated, the backend appends a random `:regen:<token>` suffix to the aibot image idempotency key, clears stale image/publish metadata only after aibot accepts the new request, and publish now uses the current image idempotency key from metadata so the newly generated asset is published.

## Prevention

- Keep primary image generation idempotent, but make manual regeneration an explicit non-idempotent operation.
- Store the accepted aibot image idempotency key on the snapshot and use it for later publish/status flows.
- Cover ready-image regeneration with backend and frontend regression tests.
