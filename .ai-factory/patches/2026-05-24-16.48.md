# Persistent shop upload storage

**Date:** 2026-05-24 16:48
**Files:** `diaverseapi/app/core/settings.py`, `diaverseapi/app/main.py`, `diaverseapi/app/cabinet/shop/admin_service.py`, `diaverseapi/docker-compose.dev.yml`, `diaverseapi/docker-compose.prod.yml`, `diaverseapi/.gitlab-ci.yml`, `diaverseapi/tests/test_cabinet_shop_admin.py`
**Severity:** medium

## Problem

Staff-uploaded shop bundle images were stored under `/static/shop/uploads`, but on production that path resolved inside `/home/diaverse/static`. The deployment process rewrites `/home/diaverse` with `rsync --delete`, so uploaded files could disappear after deploy/recreate while database rows still pointed to the old `/static/shop/uploads/...` URL.

## Root Cause

Shop image uploads reused repository-owned static storage. That directory is suitable for committed product assets, but not for admin/user-generated runtime uploads. Advent backgrounds and feedback screenshots already used dedicated `/home/storage/...` mounts, but shop uploads did not follow that persistence pattern.

## Solution

Added `SHOP_UPLOADS_DIR` with a production default of `/app/uploads/shop-uploads`, mounted it separately at `/static/shop/uploads`, and changed shop admin image upload writes to use that directory while preserving the public URL prefix. Added deployment mkdir/volume config and a regression test that verifies configured persistent storage is used instead of `BASE_DIR/static`.

## Prevention

- Runtime uploads must be stored outside deploy-synced app directories.
- Any new `/static/...` upload path needs an explicit persistent host mount or object storage backend.
- Tests should assert that configurable upload directories are used for user-generated assets.
