# Referral mentor endpoint failed without a published ruleset

**Date:** 2026-07-22 15:03
**Files:** dev runtime state (`referral_rulesets`, `referral_admin_audits`)
**Severity:** high

## Problem

After enabling the referral runtime flags on the development environment,
`GET /v1/referrals/me/mentor` returned HTTP 500. Referral link creation was
also unable to operate safely.

## Root Cause

The additive referral migrations create the ruleset tables but intentionally
do not publish an economic ruleset. All referral flags were enabled before the
required initial immutable V1 ruleset had been published. The Mentor projection
therefore could not resolve an active ruleset and raised
`active referral ruleset is unavailable`.

## Solution

Published the code-owned `INITIAL_RULESET` through `ReferralAdminService` in
the development environment. This used the canonical config validator and
checksum generator, a deterministic idempotency key, and the normal referral
admin audit boundary. Verification confirmed one active version-1 ruleset,
the expected checksum, an audit entry, and HTTP 200 from the authenticated
Mentor endpoint.

## Prevention

- Treat initial ruleset publication as a required rollout gate before enabling
  `referrals.read_enabled`, link creation, qualification, or economic flags.
- Add a deployment smoke check that requires one active referral ruleset before
  referral flags may transition to enabled.
- Keep ruleset publication inside the domain service; do not hand-insert config
  or checksum values with SQL.
- Verify the authenticated Mentor endpoint after every referral rollout.
