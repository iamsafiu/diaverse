# Advent Analytics 500 From SQLAlchemy Row Results

**Date:** 2026-04-21 23:39
**Files:**
- `diaverseapi/app/analytics/usecases.py`
- `diaverseapi/tests/test_analytics_advent.py`

**Severity:** high

## Problem

`GET /v1/analytics/advent?date_from=2026-03-22&date_to=2026-04-21` returned `500 Internal Server Error` on dev.

The traceback showed:

```text
AttributeError: uuid
```

inside `GetAdventAnalyticsUseCase._calendar_option(line)`, where `line.uuid` was accessed.

## Root Cause

The Advent analytics use case assumed `session.exec(select(CabAdventLine)).all()` returns `CabAdventLine` instances directly.

On the dev backend session implementation, the same query returned SQLAlchemy `Row` objects containing the ORM entity. A `Row` does not expose `uuid` directly, so `line.uuid` failed before the endpoint could return the intended empty-state payload.

The original unit tests used model instances directly, so they did not cover production-like `Row((CabAdventLine,))` results.

## Solution

Added `_unwrap_entity(row, model_type, source)` to normalize ORM-select results before use.

The helper supports:

- direct ORM model instances
- SQLAlchemy `Row` mappings containing the model
- positional rows/tuples where the model is at index `0`

It logs debug messages with prefix `[FIX:advent-analytics-row]` when a row wrapper is unwrapped.

Applied the helper to:

- calendar option queries
- Advent item queries

Added a regression test that feeds tuple-wrapped `CabAdventLine` and `CabAdventItem` rows and asserts the endpoint logic returns the expected `no_participants` empty state instead of crashing.

## Prevention

- When using SQLAlchemy/SQLModel sessions, do not assume ORM `select(Model)` results are always scalar model instances across all session adapters.
- Normalize entity rows at repository/usecase boundaries when code needs ORM attributes directly.
- Add tests for both direct model instances and Row-like wrapped model results when a use case calls `.all()` on ORM entity selects.
- If a query is expected to return scalars, prefer explicit `.scalars()` where the session/result type supports it, or add a small adapter that safely handles both shapes.
